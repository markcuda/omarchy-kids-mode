# V6: the project's five unknowns on Omarchy 4.0.2

Machine: omarky-air (2019 MacBook Air, T2), Omarchy 4.0.2, kernel 7.1.8-t2, encrypted install.
Started 2026-09-02. Script: `test/phase1/v6-tmpfs-exec.sh`.

## Which tmpfs mounts allow exec — DONE

| Mount | FS | Options | Exec |
| --- | --- | --- | --- |
| `/tmp` | tmpfs | `rw,nosuid,nodev,…,usrquota` | **allowed** |
| `/dev/shm` | tmpfs | `rw,nosuid,nodev,…` | **allowed** |
| `/run/user/1000` | tmpfs | `rw,nosuid,nodev,mode=700,uid=1000` | **allowed** |
| `/var/tmp` | btrfs (`@` subvolume) | `rw,…` | **allowed** |

**Finding.** A `noexec` home (spec R-FND-2) does not stop a kid from running a downloaded
binary: every writable temp location on the box allows exec. `nosuid` and `nodev` are set
everywhere, so privilege escalation through those paths is not the risk; running arbitrary
unprivileged code is.

**Consequence for the spec.** Machine-wide `noexec` on `/tmp` is off the table (I-1: it would
break the parent's own builds). The per-kid answer is a private, `noexec` `/tmp` and `/dev/shm`
for kid sessions, delivered by `pam_namespace` (polyinstantiated tmpfs with `mntopts=noexec`) on
both the SDDM stack and the `systemd-user` stack, because Omarchy launches apps through the
user's systemd manager, which does not inherit the login session's mount namespace. `/run/user/<uid>`
can be handled the same way or left as a stated fence. Tracked as a new item under issue #10
(provision) and added to the R-DESK-2 login checks.

## Limine boot menu — DONE (QEMU, Omarchy 4.0.2, limine 12.6)

Driven with `scripts/v6-limine.sh` plus hand-sent QMP keys; screenshots viewed and deleted.

| Fact | Observed |
| --- | --- |
| Menu shows | for Limine's default 5 s countdown (no `timeout:` in `/boot/limine.conf`); any key stops it |
| Entry selected | "linux" under the "Omarchy" folder; help bar offers **E Edit** and **B Blank Entry** |
| Editor content | `protocol: efi`, `path: boot():/EFI/Linux/omarchy_linux.efi#<blake2b>`, and an editable **`cmdline:`** line carrying the full kernel command line; F10 boots the edited entry |
| Blank Entry | an empty editor; any entry text can be typed and booted with F10 |
| Esc at the menu | exits Limine to the firmware boot-device list (on OVMF that includes an EFI shell) |
| Hash check | `hash_mismatch_panic: no`: the UKI hash is verified but a mismatch only warns; editing `cmdline:` does not change the hash anyway |

**So yes: `init=/bin/bash` (or `rd.break`) can be appended in the editor on a stock install.** The
kid still has to give a disk passphrase at the prompt that follows, and a kid with a slot has one.
That is a root shell on the decrypted system.

**What holds it:** `editor_enabled: no` in `/boot/limine.conf` disables both the editor and Blank
Entry. The file is generated by `limine-entry-tool` (Omarchy's `omarchy-refresh-limine` rewrites
it) and the tool's README has no editor setting, so the line must be re-asserted: by
`omarchy-kids-assert` after every pacman transaction and at every boot, and the safety check must
read it. Only the parent can regenerate the file (it needs sudo), so the exposure is one boot after
a manual refresh at worst. The firmware password remains the wall for "boot something else".

## Snapshot rollback (2026-09-02, QEMU VM)

`snapper -c root create` followed by `limine-snapper-sync` produced this entry in `/boot/limine.conf`:

```text
///1 │ 2026-09-02 20:39:16
protocol: efi
path: boot():/<machine-id>/limine_history/omarchy_linux.efi_sha256_<hash>
cmdline: ... rootflags=subvol=/@/.snapshots/1/snapshot ...
```text

Two facts follow. The entry boots a **frozen copy of the UKI** taken at snapshot time, so a
snapshot from before Kids Mode carries no `omarchy-kids-unlock` hook. It mounts the snapshot's
own `@` (system files: no polkit deny rule, no boot-login unit, the owner's stock SDDM
autologin) on top of the **live** `@home`. A kid who knows their disk password and picks an old
snapshot in the Limine menu therefore lands on the parent's desktop with the parent's files.
`editor_enabled: no` does not hide these entries, and Limine has no per-entry password.

Mitigation options, strongest first: hide snapshot entries while Kids Mode is on
(`MAX_SNAPSHOT_ENTRIES=0` in `/etc/default/limine`, re-run `limine-snapper-sync`; the parent
rolls back with `snapper rollback` from the running system, or turns the entries back on with
one command); a firmware password (out of scope); a Limine menu timeout of 0 with the menu
hidden (weak: a held key still opens it). Recorded in DECISIONS-NEEDED; the default proposed is
"hide while any kid exists", toggled by `omarchy-kids conf boot.snapshot_entries show|hide`.
Result: **mitigated** (issue #38). `omarchy-kids-assert`'s `limine-snapshots` lock
(docs/assert.md) sets `MAX_SNAPSHOT_ENTRIES=0` in `/etc/default/limine` while
`boot.snapshot_entries` (docs/conf.md, default `hide`) is `hide` and any kid exists, then runs
`limine-snapper-sync`; `show` restores the value it remembers from before. Covered by
`test/shell.d/assert-test.sh`; a QEMU VM re-run confirming the boot menu itself shows no
snapshot entries is still outstanding.
