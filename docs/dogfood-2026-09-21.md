## Findings (all observed live)

### Packaging / install

1. `PKGBUILD` has `arch=('x86_64')`; the package compiles nothing, so an
   aarch64 build is blocked for no reason. Should be `arch=('any')`.
2. Fresh install with no boot mode set: `post_install` runs
   `omarchy-kids-assert`, which fails with "cannot read trusted boot mode;
   no locks changed", and `/var/lib/omarchy-kids` is never created. The
   wizard then reports "The parent verifier is unavailable"; `authd.service`
   fails `226/NAMESPACE` (`/var/lib/omarchy-kids` missing) and its socket hits
   `start-limit-hit`. Creating the runtime dir and re-running assert fixes it.
   The runtime dirs should exist on an unprovisioned box, and a post_install
   on an unprovisioned box should not fail the package install.
3. `docs/install.md` still says `cd omarchy-kids-sandbox` (repo is
   `omarchy-kids-mode`).

### Kid UI (fable review of live screenshots, `kid-ui-review.md`)

4. The "not installed yet" Tux Paint tile takes the focus ring and can be
   selected, but cannot launch (I-6 shape). Skip it in arrow navigation or
   hide it while `apps.show_missing` is on.
5. GCompris opens its own first-run dialog (paragraph + red X) the first time
   a kid launches it; pre-seed its config at provisioning if packaging allows.
6. GCompris's bottom bar exposes a configuration wrench and a quit button to
   the kid; check where quit lands and whether config is lockable.
7. Focus ring on the unavailable tile is dimmer than on a real tile; if that
   is deliberate it is too subtle, if it is not it is an inconsistent accent.
8. At 960×540 the second row of tiles sits against the bottom edge
   (labels ~y=520); the top ~180px is empty apart from the clock.
9. "not installed yet" is ~12px low-contrast grey; Tux Paint's generic "T"
   icon is the only non-artwork tile.
10. A mouse cursor is painted on first paint of a keyboard-first UI; hide it
    until the pointer moves.

### Environment quirks (not repo defects)

- try-omarchy's guest always autologins its owner (`sddm-autologin`,
  `Automatically log in` at the image level), so the SDDM portal cannot be
  reached there by design; a per-boot drop-in was written by hand to start the
  kid session for this pass. Verify the portal on the project's own harness or
  the test laptop.
- Kid processes must run under the kid's `systemd --user` (pam_namespace on
  `systemd-user`) — launching `omarchy-kids-session` from an SSH shell is
  correctly refused by the private-`/tmp` check, and launching it as a user
  *service* fails in Hyprland (`CBackend::create() failed!`) because libseat
  needs a seat session. This is the fail-closed design working; docs could
  say so.
- `--check-setup` correctly reports the two PAM-namespace mounts as SKIP
  outside a child login.

### Loop pass (same day, Level 2): `apps.show_missing` was not enforced

The kid session was restarted at Level 2 and the picker opened (`Super+Space`). Two things were
observed live:

- Arrow-down from GCompris skipped the unavailable "Tux Paint / Not installed yet" row and landed
  on KTuberling: the `fix/launcher-skip-unavailable` navigation is working in the Level 2 picker.
- The unavailable row was still **rendered** even though `omarchy-kids-conf show kid-ada` reports
  `apps.show_missing no`. `docs/conf.md`, `docs/levels.md` and the schema say `no` (the default)
  omits a missing app's tile entirely. No production code read the key: `git log -S show_missing`
  shows it was read by `bin/omarchy-kids-session-start` in #42 (`c93e89a`) and then dropped by the
  manifest refactor (`38f878e`), while `lib/launcher-map.sh` always emitted the tile. Fixed on
  `fix/show-missing-regression`: `lib/launcher-map.sh` now omits a missing pack app's tile when the
  effective `apps.show_missing` is not `yes` and keeps it (`installed:false`, no argv) when it is.
  The queue-aware `"installing..."` caption the refactor also dropped is not restored; the kept
  tile reads `"not installed yet"` and the docs now say so.
